# Spectra 設計書

> 論文 PDF を、図表・数式・レイアウトを崩さずに日本語へ翻訳するデスクトップアプリ

- 対象 OS: Windows 10/11, macOS 12+, Linux (X11 / Wayland)
- ライセンス: AGPL-3.0（依存する PyMuPDF のライセンスに合わせる）
- 翻訳エンジン: Gemini API（Google AI Studio の無料枠）
  - 当初は DeepL API Free / Google Cloud Translation を想定していたが、DeepL API Free の新規受付終了と、
    Google Cloud / Azure がいずれもカード登録を必要とすることから、Gemini API に一本化した
  - 既定モデルは `gemini-3.5-flash-lite`（思考 `minimal`）。`gemini-3.1-flash-lite` / `gemini-3.5-flash` / `gemini-3.6-flash` /
    `gemini-3.7-flash` を選択肢とし、`gemini-3.8-flash` は混雑と無料枠の消費が大きいため非推奨として最後に置く
  - 混雑（503）・回数の上限（429）・モデルの提供終了（404）では、軽量なモデルから順に自動で切り替える（3.8 Flash は対象外）

## 1. 目的と原則

### 1.1 最重要要件

**原文 PDF のレイアウトを一切崩さないこと。** 具体的には次を保証する。

| 保証すること | 実現方法 |
| --- | --- |
| 図（ラスタ画像）を変更しない | テキスト除去時に `images=PDF_REDACT_IMAGE_NONE` を指定 |
| 図・表の罫線などベクター描画を変更しない | `graphics=PDF_REDACT_LINE_ART_NONE` を指定 |
| 図の中の文字（軸ラベル等）を変更しない | 画像・描画クラスタ領域と重なるテキストブロックは翻訳対象外 |
| 独立した数式を変更しない | 数式フォント比率の高いブロックは翻訳対象外 |
| 段落内のインライン数式を保持する | 数式スパンをプレースホルダに置換して翻訳 → 元の書体・上付き/下付き情報で再描画 |
| ページ数・ページサイズを変えない | 元 PDF を直接編集し、ページの追加削除を行わない |
| 訳文が他の要素に重ならない | 元段落の矩形内に収まるよう自動で文字サイズを調整（はみ出し禁止） |

翻訳対象外と判定したブロックは **バイト単位で一切触らない**（除去も再描画もしない）。
「迷ったら訳さない」を判定の基本方針とする。

### 1.2 デザイン原則（Apple Human Interface Guidelines を参考）

- **Clarity（明瞭さ）**: 主操作は「PDF を開く → 翻訳 → 保存」の 3 ステップのみ。主ボタンは常に 1 つだけアクセントカラーで表示する。
- **Deference（コンテンツへの敬意）**: UI は控えめなニュートラル色とし、論文のプレビューが主役になるようにする。
- **Depth / Hierarchy（階層）**: ツールバー → コンテンツ → インスペクタの 3 層構造。詳細設定はインスペクタと設定ウィンドウに退避する。
- **Consistency（一貫性）**: システムのライト/ダークモードに追従。色・角丸・余白はデザイントークンで一元管理。
- **Feedback**: 処理中は段階（解析 / 翻訳 / 組版 / 保存）と進捗を常に表示し、いつでもキャンセル可能。失敗時は原因と次の行動を日本語で示す。
- **Accessibility**: 全操作をキーボードで実行可能、アクセシブルネームを付与、コントラスト比 4.5:1 以上。

## 2. 技術選定

| 領域 | 採用 | 理由 |
| --- | --- | --- |
| 言語 | Python 3.10+ | PDF 処理ライブラリが最も成熟している |
| PDF 処理 | PyMuPDF (MuPDF) | 文字単位の座標・フォント取得、画像/ベクターを保持したテキスト除去（redaction）、フォント埋め込みとサブセット化が全て可能 |
| GUI | PySide6 (Qt 6, LGPL) | 3 OS で同一コード、HiDPI・ダークモード・D&D 対応。ネイティブに近い描画 |
| HTTP | httpx | タイムアウト・リトライ制御が容易、テスト用 MockTransport |
| API キー保管 | keyring | macOS キーチェーン / Windows 資格情報マネージャー / Linux Secret Service を統一的に利用 |
| 設定保存 | JSON + platformdirs | OS ごとの標準設定ディレクトリ |
| 配布 | PyInstaller + GitHub Actions | タグ push で 3 OS 向けバイナリを自動ビルドし Release に添付 |

### 検討して採用しなかった案

- **Electron / Tauri + Python**: 2 言語・2 プロセス構成になり配布サイズと複雑性が増す。
- **`insert_htmlbox` による訳文挿入**: ブロックごとにフォントが重複埋め込みされファイルが肥大化し、組版の細かな制御（禁則・行送り）もできない。→ 自前の組版エンジン + `TextWriter` を採用（フォントは全ページで 1 つを共有しサブセット化）。
- **非公式の Google 翻訳エンドポイント（キー不要）**: 利用規約上の問題があるため公開アプリでは採用しない。

## 4. コア処理の詳細設計

### 4.1 抽出 (extract)

`page.get_text("dict")` でブロック → 行 → スパン（フォント名、サイズ、色、フラグ、ベースライン原点、bbox）を取得する。合字（ﬁ 等）は展開する。

### 4.2 翻訳対象判定 (classify)

ブロック単位で「訳す / 訳さない」を決める。以下のいずれかに該当すれば **訳さない**。

1. 回転・縦書きのテキスト（arXiv の側面スタンプ等）
2. 画像領域、またはベクター描画クラスタ（図）の領域と面積比 50% 以上重なる
3. `find_tables()` で検出した表の領域内（表の翻訳は既定でオフ）
4. 数式フォント（CMMI, CMSY, CMEX, MSAM, MSBM, *Math* など）の文字比率が 50% 超
5. 英字を含む単語が無い（ページ番号、`(1)` などの式番号、数値のみ）
6. 英字比率が低い（表の数値セル等）
7. 等幅フォント比率が高い（コード、メールアドレス、URL）
8. 既に日本語が主体
9. 参考文献セクション（`References` 見出し以降、次の太字見出しまで。設定で変更可）

判定結果は `SkipReason` として保持し、デバッグ用レポートで確認できるようにする。

### 4.3 セグメント化 (segment)

- **行の結合**: 行末ハイフンの後に小文字が続く場合はハイフンを除去して連結。それ以外は空白で連結。
- **インライン数式**: 数式フォントのスパンと、その前後に隣接する短い記号・数字スパン（CMR の `=` `6` 等）をひとまとまりの `InlineRun` とし、訳文中では `<x id="0"/>` のような空タグで表す。Gemini にはタグを一字一句変えずに残し、日本語の語順に合う位置へ置くよう指示する。タグの表記ゆれは受信側で正規化し、欠落したタグは段落末に補うため、数式が失われることはない。
- **上付き・下付き**: 本文より小さいスパン（脚注記号など）も同様に保護し、相対サイズ・ベースラインのずれを記録して再現する。
- **引用番号** `[12]` `[3, 5–7]`: 保護対象とし、色（hyperref の緑色など）も保持する。
- **段・ページ跨ぎの段落結合**: 文末記号で終わらないブロックと、小文字で始まる次のブロック（同じ文字サイズ）を 1 つの翻訳単位にまとめる。訳文は元の文字数比で各領域に配分し、分割点は句読点を優先する。

### 4.4 翻訳 (translate)

- 未訳テキストのみを API に送る（SQLite キャッシュ: `sha256(engine, source_lang, target_lang, options, text)`）。
- バッチ: 25 段落 / 約 12,000 文字ごとに JSON の配列で送り、構造化出力（`responseSchema`）で同じ件数・順序の配列を受け取る。件数が合わない場合は分割して送り直し、安全フィルタで訳せない段落は原文のまま残す。
- リトライ: 429・5xx・タイムアウトは指数バックオフ（`Retry-After` を尊重）で最大 5 回。
- エラーは種類別の例外（認証・無料枠超過・レート制限・ネットワーク）にし、UI は日本語で原因と対処を提示。
- 事前見積もり: 翻訳前に「対象段落数」「文字数」「キャッシュ済み文字数」を表示する。
- 文体（である調 / です・ます調）は指示文で指定する。思考レベルはモデルごとの最小（3.8 Flash: `low`、3.5 Flash-Lite: `minimal`）にし、温度は Gemini 3 の推奨どおり既定値のままにする。
- 無料枠の回数制限: 1 分あたりの上限（429 + RetryInfo）は指定時間だけ待って再試行し、1 日あたりの上限は「無料枠超過」として扱い、翻訳できた分だけで PDF を作れるようにする。

### 4.5 日本語組版 (layout)

訳文を元の段落矩形に収める専用エンジン。

- **組版単位**: 和文 1 文字、欧文 1 単語、インライン数式 1 塊を分割不可の単位とする。
- **禁則処理**: 行頭禁則（`、。）」ー` 等）は行末へぶら下げ、行末禁則（`（「` 等）は次行へ送る。
- **和欧間スペース**: 和文と欧文・数字・数式の間に 1/4 em を自動挿入。
- **両端揃え**: 最終行以外は行幅いっぱいに均等配置（元論文の両端揃えに合わせる）。見出し・中央寄せのブロックは元の揃えを維持。
- **字下げ**: 元段落の 1 行目のインデントを維持。
- **行送り**: 元の行送り（ベースライン間隔の中央値）を基準にする。
- **自動縮小**: 収まらない場合は文字サイズと行送りを同率で二分探索により縮小。矩形からはみ出すことはしない。
- **領域の拡張**: 見出しなど 1 行の短いブロックは、右側（中央揃えなら両側）に他の要素が無い範囲でのみ横に広げてから組む。
- **書体**: 和文は内蔵フォント（Droid Sans Fallback）または Noto Serif JP / Noto Sans JP（アプリからワンクリックでダウンロード、OFL）/ 任意のフォントファイル。欧文は和文書体に合わせて Times / Helvetica 系、数式の斜体は Times Italic。太字は擬似ボールドで表現。

### 4.6 描画 (render)

1. 翻訳対象ブロックの **各行の矩形**（上下を僅かに縮めたもの）に塗りなしの redaction 注釈を追加。
2. `apply_redactions(images=NONE, graphics=NONE, text=REMOVE)` で **文字だけ** を除去（背景色・画像・線は残る）。
3. 組版結果を `TextWriter` で書き込み（色・太字ごとにまとめる）。和文フォントはドキュメント内で 1 つの xref を共有。
4. 保存時に `subset_fonts()` と `garbage=3, deflate=True` でサイズを最小化。

### 4.7 品質検査（自動）

翻訳後、ページごとに以下を検証しレポートする（テストでも同じ関数を使う）。

- 画像数・ベクター描画数が翻訳前後で一致すること
- 翻訳対象外ブロックのテキストが変化していないこと
- 描画した訳文がすべて割り当て矩形内に収まっていること
- 縮小率が 70% を下回った段落の一覧（読みにくい可能性がある箇所として UI に表示）

### 4.8 出力形式

| 形式 | 内容 |
| --- | --- |
| 翻訳のみ | 元 PDF と同じページ構成の日本語版 |
| 左右対訳 | 1 ページの左に原文、右に訳文（横長ページ） |
| 交互対訳 | 原文ページ → 訳文ページ を交互に並べる |

```

│  │          │          │   │          │        │  ページ すべて ▾   │
```

- **空の状態**: 中央に破線のドロップ領域、見出し「論文の PDF をドロップ」、副文、主ボタン「PDF を選択…」。API キー未設定時は「API キーを設定」への導線を表示。
- **ツールバー**: 主ボタンは状態で変化（翻訳 → 翻訳中は無効 → 完了後「書き出す…」）。書き出し時に形式をカードで選ぶ。
- **文字の大きさ**: 利用者には設定させず、元の論文の組版（原文の文字サイズ・行送り）から自動で決める。
- **プレビュー**: 原文・訳文を左右に並べ、スクロールとズームを同期。表示切替（原文 / 対訳 / 翻訳）はセグメントコントロール。
- **インスペクタ**: macOS のシステム設定風のグループ化フォーム。トグルは HIG のスイッチ。
- **設定ウィンドウ**: 「翻訳エンジン」「フォント」「詳細」の 3 タブ。API キーは伏字入力 + 表示切替 + 「接続を確認」ボタン（成功時は使用量も表示）+ キー取得ページへのリンク。変更は即時保存（HIG の環境設定の慣習）。

## 6. セキュリティとプライバシー

- API キーは OS の資格情報ストアに保存し、設定ファイルには書かない。利用できない環境（一部 Linux）では権限 600 のファイルに保存し、UI で明示する。
- 送信先は選択した翻訳 API のみ。テレメトリは一切送らない。
- ログや例外メッセージに API キーを含めない（マスク処理）。

## 7. 開発の進め方

### 7.1 ブランチ戦略

- `main`: リリース可能な状態のみ。タグ `vX.Y.Z` でリリースビルド。
- `develop`: 統合ブランチ。
- `feature/*` / `docs/*` / `ci/*`: 作業ブランチ。`develop` から切り、完了後 `--no-ff` でマージ。

### 7.2 バージョン管理

- **セマンティック バージョニング**（`MAJOR.MINOR.PATCH`）。PEP 440 と両立する形でプレリリースは `1.2.0rc1` のように書く。
  - MAJOR: 出力 PDF や設定の互換性を壊す変更 / MINOR: 機能追加 / PATCH: 不具合修正
  - 1.0.0 までは `0.x` で運用し、API や出力の互換性は保証しない
- **バージョン番号の唯一の情報源**は `src/spectra/__init__.py` の `__version__`。
  pyproject（hatch の dynamic version）、アプリの「Spectra について」、CLI の `--version`、
  ビルド成果物のファイル名、macOS の `CFBundleShortVersionString`、Windows のファイルバージョンはすべてここから取得する。
- **CHANGELOG.md**（Keep a Changelog 形式）に変更を `Unreleased` 節へ随時追記する。
- **リリース手順**
  1. `python scripts/bump_version.py {major|minor|patch|X.Y.Z}` — `__version__` を更新し、`Unreleased` を新バージョンの節に確定
  2. `develop` でコミット → `main` へ `--no-ff` マージ → 注釈付きタグ `vX.Y.Z` を作成して push
  3. GitHub Actions がタグを検知し、`scripts/check_version.py` でタグ・`__version__`・CHANGELOG の一致を検査してから 3 OS 向けにビルドし、CHANGELOG の該当節を本文にした Release を作成する
- 初回リリースは `python scripts/bump_version.py 0.1.0`（現在値と同じ番号を明示して確定）

### 7.4 テスト方針

- 著作権の都合上、実際の論文はリポジトリに含めない。テストでは PyMuPDF で **図・数式・表・2 段組を含む合成 PDF** を生成して検証する。
