# v0.4 の要件と設計

この文書は、v0.4 で行う開発の要件・設計・分担をまとめたものです。利用者の判断（§8）を反映しています。
実装は、分担（§9）の了承の後に始めます。

v0.4 で行うこと（段階に分けず、すべて v0.4 に入れる）:

1. 複数の API キーと、無料枠の上限に達したときの自動切り替え（§3）
2. 更新の通知（§4）
3. PDF の表示の機能の向上（§5）
4. 右のパネルの整理（論文の詳細・AI 翻訳の詳細・ノート）と、ノートの同期（§6）

---

## 1. 目的と範囲

**目的**: 翻訳を止まりにくくし（複数のキー）、読みやすくし（PDF の表示）、読みながら書き留められるようにする（ノート）。更新にも気づけるようにする。

**変えないこと**

- 翻訳のプロバイダは Gemini だけ。標準の API の設定（既定のモデル `gemini-3.5-flash-lite`、混雑時のモデルの自動切り替え）は今のまま。
- API キーは OS の資格情報ストアにだけ置く（使えない環境では今の権限 600 のファイル）。設定ファイル・同期フォルダ・ログに書かない。
- テレメトリは送らない。増える通信先は更新の確認の `api.github.com` だけ（§4）。
- 同期フォルダの形式（`FORMAT = 1`）は変えない。ノートは古い版が無視できる形で足す（§6.3）。

**範囲外**: Gemini 以外のプロバイダ（DeepL・OpenAI 互換・Claude など）、論文を複数のタブで開くこと、注釈・ハイライト、AI の読書支援、
自動での置き換え（ダウンロードして入れ替える）更新、左のアイコンの列。
プロバイダの追加に備えた下準備は、キーの目録にプロバイダの欄を持たせる（§3.2）ことに留める。

## 3. 複数の API キーと自動切り替え

### 3.1 要件

- Gemini のキーを複数登録し、名前（例: 「研究室」「個人」）を付け、順序を並べ替えられる。
- 1 日の無料枠の上限に達したら、次のキーへ自動で切り替えて翻訳を続ける（設定「上限に達したら次のキーに切り替える」、**既定はオン**）。

### 3.2 データモデル

設定ファイルにはキーの**目録だけ**を置き、中身は資格情報ストアに置く。

```jsonc
// settings.json（キーの中身は書かない）
"api_keys": [                                   // この順に使う（先頭が最初に使うキー）
  {"id": "default", "provider": "gemini", "label": "Gemini"},   // 今のキー（移さない）
  {"id": "3f9c0a…", "provider": "gemini", "label": "研究室"}
],
"key_auto_switch": true
```

- 資格情報ストアのアカウント名: `default` は今の `gemini-api-key` をそのまま使い、新しいキーは `gemini-api-key-<id>`（`id` は uuid4 の 16 進）。
  今のキーを書き直さないので、macOS でキーチェーンの許可を求められる回数は増えない（アドホック署名のアプリはビルドごとに別のアプリとして扱われる）。
- 起動時は、先頭のキーの有無だけを確かめる（`has()`。macOS では中身を読まない）。中身は使う直前に、そのキーだけを読む。切り替えで初めて読むキーは、macOS で 1 回許可を求められることがある。
- 目録とラベルに、キーの一部（先頭・末尾）は書かない。画面では資格情報ストアから読んだときだけ `mask()` で伏せて表示する。
- 環境変数（`SPECTRA_GEMINI_API_KEY` など）があれば、今と同じくそれだけを使い、切り替えはしない（画面に「環境変数 … を使用中」）。
- キーの目録・上限の記録は同期しない（ほかのパソコンには中身がない）。
- 古い設定（版 5）を読んだら、資格情報ストアに `gemini-api-key` があれば `{"id": "default", "label": "Gemini"}` の 1 件の目録を作る。

### 3.3 切り替えの設計

**上限の検出**（`gemini.py` の `_raise_for_status` の今の分類を使う）

| 応答 | 分類 | キーの扱い |
| --- | --- | --- |
| 429 / `RESOURCE_EXHAUSTED` で、上限の ID に `PerDay` を含む | `QuotaExceededError` | そのキーとモデルの組を「今日は上限」として記録し、すぐに次のキーへ |
| 429 で 1 分あたりの上限 | `RateLimitError` | 今と同じく `Retry-After` だけ待って再試行。再試行を使い切ったら次のキーへ（記録はしない） |
| 400 `API_KEY_INVALID` / 401 / 403 | `AuthenticationError` | 先頭のキーなら今と同じくエラー。切り替えの途中のキーなら、そのキーを飛ばし、「キー『…』が正しくありません」と知らせる |
| 5xx・混雑 | `ServiceError` など | キーは切り替えない（キーの問題ではない）。今と同じくモデルの自動切り替えに任せる |

**順序**: 利用者が選んだモデルのまま、目録の順にキーを試す。すべてのキーがそのモデルで上限なら、今のモデルの自動切り替え（`FALLBACK_ORDER`）で次のモデルに移り、そのモデルでまた目録の順にキーを試す。
（無料枠はモデルごと・プロジェクトごとに数えられるので、モデルより先にキーを切り替える方が、選んだモデルの品質を保てる。）

**上限の記録**: `{(キーの id, モデル): 戻る時刻}` を、設定フォルダの `quota.json` に置く（キーの中身は書かない）。戻る時刻は米国太平洋時間の次の 0 時
（`zoneinfo`。Windows では `tzdata` が要る。使えなければ 24 時間後）。記録のあるキーは、その時刻まで試さない（毎回上限のキーに問い合わせて無駄に待たない）。

**通知**

- 翻訳中: 進み具合の行の下に 1 行「API キー『研究室』が今日の上限に達したため、『個人』に切り替えました」。モデルの切り替え（今の `notices`）も同じ場所に出す。
- すべてのキーが上限: 今の `PartialTranslationError`（訳せた分は保存済み、続きから再開）に「登録したすべてのキーが今日の上限に達しました。上限は日本時間の 17 時（米国の夏時間の間は 16 時）ごろに戻ります。」
- 設定のキーの一覧: 上限のキーに「今日の上限（17:00 ごろに戻ります）」と表示する。
- 切り替えがオフ: 今と同じく止まり、「設定で次のキーを選ぶか、自動切り替えをオンにしてください」と案内する。

**キャッシュ**: キーは `cache_namespace()` に入れない（今のまま）。キーを切り替えても、訳文のキャッシュはそのまま使われる。

## 4. 更新の通知

方式は**通知だけ**。ダウンロードとアプリの入れ替えは利用者がブラウザで行う（未署名の配布版では、アプリ自身が入れ替えるのは安全でないため）。

- **初回に尋ねる**: 新しく入れた人は最初の起動で、v0.3 以前から更新した人は更新後の最初の起動で、「新しいバージョンを確認しますか？（GitHub に問い合わせます）」と 1 回だけ尋ねる。答えは設定の `update_check`（未回答 / オン / オフ）。設定の「詳細」でいつでも変えられる。
- 確かめる先は `https://api.github.com/repos/myuto2490/Spectra/releases/latest` だけ。送るのは通常の HTTPS の要求と User-Agent（今の `Spectra (+https://github.com/myuto2490/Spectra)`）。端末の ID・ライブラリの情報は送らない。GitHub には IP アドレスが見える。
- 起動時に、前回から 24 時間以上たっていれば確かめる（`update_last_checked`）。失敗しても何も表示しない。設定の「詳細」に「今すぐ確認」を置く（こちらは失敗も表示する）。
- 下書き・プレリリースは除く。版は数字の組で比べる（`0.10.0 > 0.9.0`）。
- 新しい版があれば、ライブラリ画面の上の帯（今の `banner`）に「Spectra 0.5.0 が利用できます [ダウンロード] [あとで] [この版を通知しない]」を出す。
- 開く URL は `https://github.com/myuto2490/Spectra/releases/` で始まるものだけ（応答の URL をそのまま信じない）。
- SECURITY.md の「外部への通信」に、更新の確認（送信先・送る内容・無効にする方法）を足す。

## 5. PDF の表示の機能

機能性が上がるものを積極的に入れる。今の `pdf_view.py` は、ページごとの画像を並べる表示（原文・訳文の 2 つを同期）。

| 機能 | 内容 | 優先 |
| --- | --- | --- |
| ページ n/N とページ指定 | ツールバーに「‹ [ 3 ] / 15 ›」。番号を入れて Enter で移動。PageUp/PageDown・Home/End | 必須 |
| PDF 内の検索 | 読書画面では ⌘F（Ctrl+F）で検索欄を開き、原文・訳文のうち表示中のものを検索（PyMuPDF の `search_for`）。一致を色で示し、↩ / ⇧↩ で次・前へ、「3 / 12 件」を表示 | 必須 |
| ズームの改善 | 「幅に合わせる」に加えて「ページ全体」、倍率の一覧（50〜400%）、⌘＋スクロール・ピンチでのズーム（ポインタの位置を中心に）、論文ごとに倍率と位置を覚えて次に開いたときに戻す | 必須 |
| 読書画面での情報の表示 | 右のパネルの「論文の詳細」（§6.1） | 必須 |
| 文字の選択とコピー | ドラッグで文字を選び、⌘C でコピー（引用・メモ用） | 推奨 |
| ページの一覧（サムネイル） | 左に開閉できるサムネイルの列。クリックでそのページへ | 推奨 |
| PDF 内のリンク | 目次・参考文献・URL のリンクをクリックで移動・ブラウザで開く（外へのリンクは確認してから） | 推奨 |
| 目次（しおり） | PDF のしおりがあれば一覧を出す | 余裕があれば |

検索とページの移動のキーボード操作は `docs/DESIGN.md` §5.3 にも足す。⌘F はライブラリ画面では今と同じくライブラリの検索。

## 6. 右のパネルとノート

### 6.1 右のパネル

ライブラリ画面の詳細パネルと読書画面の右のパネルを、同じ 3 つのタブにそろえる。

| タブ | 内容 |
| --- | --- |
| 論文の詳細 | 今の「論文の詳細」（書誌情報・ファイル・情報を編集…・BibTeX）。読書画面でも同じ部品を使う |
| AI 翻訳の詳細 | 今の「AI 翻訳の詳細」（状態・モデル）。読書画面では、今のインスペクタ（モデル・出力・翻訳対象・見積もり）もここに入れる |
| ノート | 論文ごとのメモ（プレーンテキスト）。入力をやめて 1 秒後に自動で保存。最終更新の時刻と、同期で連結されたときの印 |

右のパネルは開閉でき、選んでいたタブと幅を覚える。

### 6.2 ノートの保存

- ライブラリの DB の論文の表に `note TEXT NOT NULL DEFAULT ''` と `note_updated_at REAL` を足す（ライブラリの `SCHEMA_VERSION` を上げる。マイグレーションは列の追加だけ）。
- 長さの上限は 100,000 文字。`Library.set_note(paper_id, text)` が保存とイベント（`note`）の通知を行う。
- 書誌情報の照会・再翻訳ではノートを変えない。論文をゴミ箱に入れて戻したときはノートも戻る。BibTeX には含めない。

### 6.3 ノートの同期（2 台で同時に書いたら両方を残して連結）

state ファイル（`papers/<sha>/state.<端末>.json`）に、`fields` とは別の項目 `note` を足す。古い版は知らない項目を無視するので、`FORMAT` は 1 のまま。

```jsonc
"note": {"text": "…", "hlc": "<HLC>", "parents": ["<HLC>", …]}   // parents: この内容のもとにした版の hlc
```

**比べ方**（自分の版 L と相手の版 R）

1. 中身が同じなら、hlc の大きい方を採る（連結しない）。
2. R の `parents` に L の hlc があれば、R は L を見てから書いたので R を採る（逆も同じ）。
3. どちらでもなければ同時に書かれたので、連結する: hlc の大きい方の本文の後に、
   `\n\n――― 「<端末の名前>」で同時に編集された内容 ―――\n` と小さい方の本文。新しい版の `parents` は両方の hlc。
   連結の結果は両方の端末で同じになり、1 によって再び連結されることはない（往復しない）。
4. 3 台以上でも、hlc の順に並べてから 2 つずつ同じ規則で畳む（どの端末でも同じ結果になる）。

- 連結したときは、ノートのタブに「ほかのパソコンでの編集と連結しました」と出す（同期の変更の一覧にも載せる）。
- 中身は外部入力として検証する（文字列、上限の長さ、`clean_text` で見えない文字を除く。改行は残す）。
- 詳しい規則とテストの表は `docs/SYNC.md` に節を足して書く。

## 7. テストの方針（ネットワークを使わない）

- **キーと切り替え**: `httpx.MockTransport` で、キーごと・モデルごとに 200・429（PerDay / PerMinute）・400 `API_KEY_INVALID`・5xx を返す偽のサーバーを作り、
  切り替えの順序（キー → モデル）、上限の記録と戻る時刻（時計を差し替える）、無効なキーを飛ばすこと、環境変数があるときは切り替えないこと、
  切り替えがオフのときに止まること、通知の文言、キーを切り替えてもキャッシュが使われることを確かめる。
- **キーの保管**: `SecretStore(use_keyring=False)` と偽の `keyring` で、追加・削除・並べ替え、今の `gemini-api-key` がそのまま 1 本目になること、
  設定ファイルと `quota.json` にキーの中身が出ないこと。版 5 の設定からの移行。
- **更新の通知**: 偽の応答で、新しい版・同じ版・プレリリース・下書き・`releases/` 以外の URL・失敗（何も出さない）・24 時間に 1 回・オフや未回答のときに通信しないこと。
- **PDF の表示**: `pdf_factory` で作る PDF で、ページの移動、検索の件数と移動、ズームの倍率と位置の記憶、文字の選択（`pytest-qt` と offscreen）。
- **右のパネルとノート**: タブの切り替えと記憶、ノートの自動保存。
- **ノートの同期**: `test_sync_scenarios.py` の型で、片方だけの編集・順に編集・同時の編集（連結し、往復しない）・3 台・同じ中身・古い版の state ファイルとの混在・不正な値。
- CI は今と同じく 3 つの OS で回す（Windows の更新時刻・シンボリックリンク・時計の粗さに注意。v0.3.0 の失敗を参照）。

### 9.2 取り込みの順番（`develop` へ）

| 順 | ブランチ | 理由 |
| --- | --- | --- |
| 1 | `feature/settings-v6`（A） | 全員が使う設定の項目を先に入れる。小さい |
| 2 | `feature/notes-sync`（C） | E が使う `Library.set_note` と DB の版上げを先に入れる |
| 3 | `feature/update-check`（D） | 独立している |
| 4 | `feature/multi-keys`（B） | 設定画面と翻訳の内側。ほかと重ならない |
| 5 | `feature/side-panel`（E） | C の後 |
| 6 | `feature/pdf-view`（F） | `main_window.py` に D・E を組み込むので最後 |

作業は並行して進め、取り込みはこの順に行う。各ブランチは取り込みの前に `develop` を取り込み直し、ruff と pytest（3 つの OS の CI）が通ることを確かめる。
