# 次の開発（v0.4 以降）の要件と設計

この文書は、次の 4 つの依頼について、要件・設計・導入の順序と、実装の前に利用者に決めてもらう判断をまとめたものです。
実装はこの文書の承認後に行います。

1. Mendeley を参考にした機能の拡張と UI の向上
2. アプリの自動更新
3. 複数の API キーの登録
4. Gemini 以外の翻訳プロバイダを設定で選べるようにする（既定は今のまま Gemini）

---

## 1. 目的と範囲

**目的**: 論文を「訳して読む」だけでなく、「並べて読み、書き込み、整理する」ところまで Spectra で完結させる。
あわせて、翻訳の手段（プロバイダとキー）の選択肢を増やし、更新の手間を減らす。

**変えないこと**

- 既定の翻訳は Gemini（`gemini-3.5-flash-lite`、自動切り替えあり）。新しく入れた人も、更新した人も、何も操作しなければ今と同じ動き。
- API キーは OS の資格情報ストアにだけ置く（使えない環境では今の権限 600 のファイル）。設定ファイル・同期フォルダ・ログに書かない。
- テレメトリは送らない。通信先が増える機能（自動更新・新しいプロバイダ・AI の読書支援）は、何を・どこへ送るかを設定画面と SECURITY.md に書く。
- 同期フォルダの形式（`FORMAT = 1`）は、注釈・ノートを同期するまで変えない（§6.4）。

**範囲外（今回はしない）**: 共有ライブラリ・グループ、Web 版、引用スタイル（CSL）での参考文献の出力、ブラウザ拡張。

## 3. 複数の API キー

### 3.1 使い道

- 研究室のキーと個人のキー、無料枠のキーと有料のキーを登録しておき、切り替える。
- プロバイダを切り替えても、それぞれのキーが残る。

**注意**: 無料枠の上限を超えるために、同じ人が複数のキー（Google Cloud の複数のプロジェクト）を順に使うことは、
各社の利用規約に反するおそれがあります。そのため、**上限に達したときに別のキーへ自動で切り替える機能は、既定では入れません**
（入れるかどうかは §9 の判断 3）。上限に達したときは、今と同じく別のモデルへの自動切り替えと、キーを選び直す案内だけにします。

### 3.2 データモデル

設定ファイル（`settings.json`）にはキーの**目録だけ**を置き、中身は資格情報ストアに置く。

```jsonc
// settings.json（キーの中身は書かない）
"engine": "gemini",                         // 今のまま。選んでいるプロバイダ
"models": {"gemini": "gemini-3.5-flash-lite", "deepl": "", "openai_compat": "llama3.1:8b"},
"api_keys": [
  {"id": "default", "provider": "gemini", "label": "Gemini"},           // 今のキー（移さない）
  {"id": "3f9c…",   "provider": "gemini", "label": "研究室"},
  {"id": "a71e…",   "provider": "deepl",  "label": "DeepL Free"}
],
"active_key": {"gemini": "3f9c…", "deepl": "a71e…"}
```

- 資格情報ストアのアカウント名: `default` は今の `gemini-api-key` をそのまま使い、新しいキーは `<provider>-api-key-<id>`。
  今のキーを書き直さないので、macOS でキーチェーンの許可を求められる回数が増えない（`secrets.py` の注記のとおり、アドホック署名のアプリはビルドごとに別のアプリとして扱われる）。
- ラベルは利用者が付ける名前だけ。キーの先頭・末尾などは目録に書かない（画面では資格情報ストアから読んで `mask()` で伏せて表示）。
- 起動時に読むのは、使うキーの有無（`has()`。macOS では中身を読まない）だけ。中身は翻訳・接続の確認の直前に、使うキーだけを読む（キーを N 本登録しても、許可を求められるのは使うキーの分だけ）。
- 環境変数は今と同じく最優先で、プロバイダごとに持つ（`SPECTRA_DEEPL_API_KEY` など）。設定画面では「環境変数 … を使用中」と表示し、一覧は編集できるが使われないことを示す。
- `gemini_model` は `models["gemini"]` に移し、古い設定を読んだときに変換する（`SCHEMA_VERSION` 6）。古い版の Spectra で新しい設定を開いても壊れないよう、`gemini_model` も当面は書き続ける。
- 同期しない（今と同じ。キーの目録も、ほかのパソコンの資格情報ストアに中身がないので意味がない）。
- キーを削除したら資格情報ストアからも消す。使用中のキーを消したら、そのプロバイダの残りのキーの先頭を使う（なければ未設定）。

## 4. 翻訳プロバイダ

### 4.1 候補の比較

料金と無料枠は変わりやすいので、実装の時点で各社のページで確かめ、画面には「キーを取得」のリンクと要点だけを出す。

| 候補 | 無料枠 | 論文の日本語の質 | `<x id/>`（数式などの保護）の扱い | 実装の手間 | 備考 |
| --- | --- | --- | --- | --- | --- |
| **Gemini**（今） | あり（回数の上限） | 良い | 指示で残す（実装済み） | 済み | 既定のまま |
| **DeepL API** | Free プランあり（月の文字数の上限） | 良い。文体の指定（です・ます / である）に対応 | `tag_handling=xml` でタグを保ったまま訳せる | 小 | 使用量を API で取得できる（`Usage` に合う）。LLM でないので指示文は使わない |
| **OpenAI 互換**（OpenAI・OpenRouter・Ollama・LM Studio など） | 提供元による。Ollama などの手元のモデルは無料 | モデルによる | 指示で残す（Gemini と同じ方式） | 小〜中 | 1 つの実装で多くの提供元に届く。送信先の URL を利用者が入れるので、http を許すのは localhost だけにする |
| **Claude（Anthropic API）** | なし（従量課金） | 良い | 指示で残す | 小 | `llm.py` ができれば薄い実装で済む |
| Google Cloud Translation | あり（請求先の登録が必要） | 普通 | HTML モードで保てる | 中 | 請求先の登録が要り、Gemini と比べて利点が小さい |
| Microsoft Translator | あり | 普通 | HTML モードで保てる | 中 | 同上 |

**おすすめ**: 第 1 段階は **DeepL** と **OpenAI 互換**（手元の LLM を含む）。どちらも需要が大きく、性格が違う
（DeepL は無料枠と安定、OpenAI 互換は選択肢の広さと「本文を外に出さない」手元の実行）。Claude はその次（§9 の判断 4）。

### 4.2 抽象化

```
Translator（base.py: バッチ・リトライ・キャンセル。今のまま）
 ├─ LLMTranslator（llm.py: 指示文・JSON 出力・タグの検証・壊れた出力の検出）
 │    ├─ GeminiTranslator   … API の呼び出し、モデルの自動切り替え
 │    ├─ OpenAICompatTranslator … base_url・model を受け取る
 │    └─ ClaudeTranslator（後で）
 ├─ DeepLTranslator … tag_handling=xml、formality、usage()
 └─ DummyTranslator
```

- `ProviderInfo`（registry）: `id`・名前・説明・キーの取得先・`needs_key`・`models`・`supports_formality`・`send_to`（画面と SECURITY.md に出す送信先）・`base_url_editable`。
- `create(provider, model, key, **kw)` に揃え、Gemini だけの分岐（`auto_fallback`）は `ProviderInfo` の能力として持つ。
- キャッシュのキー（`cache_namespace()`）にはプロバイダ・モデル・指示文の版を入れる（キーは入れない）。今の Gemini の訳文のキャッシュはそのまま使える。
- 訳文の情報（`Translation.model`）には「プロバイダ / モデル」を入れ、ライブラリと同期の画面で区別できるようにする。同期の形式は変わらない（文字列のまま）。
- エラーは今の `errors.py` の種類（認証・上限・混雑・ネットワーク）に各社の応答を対応させ、画面の文言を共通にする。

## 5. 自動更新

### 5.1 方式の比較

| 方式 | 内容 | 安全性（今の未署名の配布版で） | 手間 |
| --- | --- | --- | --- |
| **A. 通知だけ** | GitHub の最新リリースを確かめ、新しい版があれば知らせて、リリースのページを開く | 高い。入れ替えは利用者がブラウザで行うので、macOS の Gatekeeper などの確認も今と同じく働く | 小 |
| B. ダウンロードして検証まで | アプリがファイルを取り、`SHA256SUMS.txt` と照合して、Finder・エクスプローラーで示す | 中。同じリリースの `SHA256SUMS.txt` は壊れたダウンロードを見つけられるが、GitHub のアカウントが乗っ取られたときの偽物は防げない | 中 |
| C. 置き換えまで自動 | ダウンロードして、アプリを入れ替えて再起動（macOS は Sparkle、Windows は自前の入れ替え） | 署名がないと低い。リリースが乗っ取られると、全利用者のパソコンで偽のコードが動く。アプリが取ったファイルには隔離属性が付かず、Gatekeeper の確認も通らない | 大 |

C を安全にするには、アプリに埋め込んだ公開鍵での更新の署名（Sparkle の EdDSA、または minisign）と、OS のコード署名（`docs/CODE_SIGNING.md`）が前提になる。
また macOS では、アドホック署名のままアプリを入れ替えると、キーチェーンの許可を毎回求められる（§3.2）。

**おすすめ**: 第 1 段階は **A（通知だけ）**。B・C はコード署名を整えてから検討する。

### 5.2 通知の仕様（A）

- 確かめる先は `https://api.github.com/repos/myuto2490/Spectra/releases/latest` だけ。送るのは通常の HTTPS の要求と User-Agent（`Spectra/<版>`）で、端末の ID・ライブラリの情報は送らない。GitHub には IP アドレスと版が見える。
- 起動のたび、ただし 1 日に 1 回まで。失敗しても何も表示しない。設定の「詳細」で「今すぐ確かめる」も置く。
- 下書き・プレリリースは除く。版の比較は `packaging.version` 相当（`0.10.0 > 0.9.0`）。
- 新しい版があれば、ライブラリ画面の上に帯（今の `banner`）で「Spectra 0.4.0 が利用できます [リリースノート] [あとで] [この版は通知しない]」。
- リリースのページの URL は `https://github.com/myuto2490/Spectra/releases/` で始まるものだけを開く（API の応答をそのまま信じない）。
- **既定でオンかオフか**は利用者の判断（§9 の判断 5）。おすすめは「初回起動時に 1 回だけ尋ねる」。既存の利用者には、更新後の最初の起動で尋ねる。
- SECURITY.md の「外部への通信」に、更新の確認（送信先・送る内容・無効にする方法）を足す。「テレメトリを送らない」は変わらない。

## 6. Mendeley を参考にした UI

### 6.1 参考画像から読み取れる機能

左の細いアイコンの列（ライブラリ・ノートブック・検索・同期）、論文を**タブで複数開く**（入りきらない分は「19 more」）、
PDF のツールバー（選択・ハイライト・コメント、色、ページの移動、ズーム、回転、保存、検索）、
右のパネルのタブ（**Info / Annotations / Notebook / Reading Assistant**）、
Info の **Key information**（種類「Journal article」と変更、著者・年・月・日・号・雑誌・言語・ページ・訳者・巻を、その場で編集。空の項目は「Add day」のような薄い文字）。

Spectra の今: 画面はライブラリと読書の 2 枚（`QStackedWidget`）で、読書画面は 1 本ずつ。読書画面の右は翻訳の設定だけで、書誌情報は出ない。
ライブラリの詳細パネルには「論文の詳細 / AI 翻訳の詳細」の 2 つのタブがあり、著者・年・雑誌・巻・号・ページ・DOI・arXiv・概要・URL を表示する（編集は「情報を編集…」のダイアログ）。
ページ番号の入力と PDF 内の検索はない（⌘F はライブラリの検索）。注釈・ノートの機能はない。

### 6.4 同期への影響

- 書誌の項目を足すだけなら、同期の形式は変わらない（知らない項目は古い版が無視する。`files.py` の `SYNC_FIELDS`）。
- ノートは 1 つの項目として HLC で比べる（後に書いた方が勝つ）。2 台で同時に書くと片方が消えるので、競合したら両方を残す（「競合したノート」として連結）かを決める（§9 の判断 7）。
- 注釈は 1 件ずつ ID と HLC を持つ記録にすれば、今の仕組み（コレクションの所属と同じ形）で同期できる。同期フォルダの形式を上げる（`FORMAT = 2`）必要があるかは、実装の前に `docs/SYNC.md` で設計する。

## 8. テストの方針（ネットワークを使わない）

- **プロバイダ**: `httpx.MockTransport` で各社の応答（成功・401・429 と Retry-After・上限・壊れた JSON・件数の不一致・タグの欠落）を再現する。
  `Translator` の共通のテスト（件数・順序・`<x id/>` の保持・キャンセル・リトライ）を、すべてのプロバイダに同じ表で当てる。
- **キー**: `SecretStore(use_keyring=False)` と、資格情報ストアの偽物（`keyring` の `set_keyring` で差し替え）で、追加・削除・選択・環境変数の優先・
  今のキー（`gemini-api-key`）がそのまま 1 本目になること・設定ファイルにキーの中身が出ないことを確かめる。
- **設定の移行**: `SCHEMA_VERSION` 5 の設定を読んで 6 に変換し、`gemini_model` の値が保たれること。新しい設定を古い形でも読めること。
- **更新の通知**: 応答の偽物で、新しい版・同じ版・プレリリース・下書き・不正な URL・失敗（何も表示しない）・1 日 1 回・オフのときに通信しないこと。
- **UI**: 今の `pytest-qt` と offscreen で、タブの開閉と開き直し、右のパネルの切り替え、その場での編集の保存。
- **同期**: 書誌の項目を足したとき、古い版の state ファイルと混ざっても壊れないこと（`test_sync_scenarios.py` の型で）。
- CI は今と同じ 3 つの OS で回す（Windows の更新時刻・パスの違いに注意。v0.3.0 での失敗を参照）。
