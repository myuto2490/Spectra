## 1. 目的と範囲

別のパソコンで Spectra を起動して連携すると、これまで読み込んだ論文（ライブラリ・原文・訳文）を読めるようにする。

- 対象: 同じ人が使う複数台のパソコン（Windows / macOS / Linux）。台数は 2〜3 台を想定する。
- 対象外: 複数人での共有、Web 版・モバイル版、リアルタイムの共同編集、Spectra 独自のサーバー。

## 2. 結論の要約

| 項目 | 結論 | 合意 |
|---|---|---|
| 連携の方式 | 同期フォルダ方式（Google Drive・Dropbox・iCloud・OneDrive などのアプリが同期するフォルダに書き出す） | f3・e7・5d・97 |
| 既定 | オフ（オプトイン） | e7・5d・97 |
| 同期の形式 | 論文ごと・端末ごとの状態ファイル（JSON）＋ 内容のハッシュを名前にした PDF。SQLite は同期フォルダに置かない | f3・e7 |
| マージ | 項目ごとの LWW。時刻はハイブリッド論理時計（HLC）。手で編集した値を優先 | f3・e7 |
| 同期するもの | 書誌情報・お気に入り・コレクション・原文 PDF・訳文 PDF | f3・e7・5d |
| 同期しないもの | API キー・設定・翻訳キャッシュ・端末ごとの状態（照会の状態、取り込み元のパス） | f3・e7・5d |
| 書き手 | 各端末は自分の名前のファイルにだけ書く（端末ごとに単一の書き手）。共有ファイルは、内容が変わらない `original.pdf` を「まだ無いときだけ」作る場合だけ | f3・e7 |
| ローカルの同期情報 | 別ファイルの `sync.sqlite3` に置き、`library.sqlite3` は変えない（v0.2.0 に戻してもライブラリが開ける） | f3・e7 |
| 同期フォルダの読み書き | UI のスレッドから決して直接読まない。すべてワーカーで行い、PDF は手元のライブラリにコピーして sha256 を検証してから開く | f3・e7・5d |

## 3. 現在の構造（v0.2.0）と、同期での危険

e7 がコードで確認した内容。

| 対象 | 場所・形式 | 同期での危険と対応 |
|---|---|---|
| ライブラリ | `data_dir()/library/library.sqlite3`（WAL） | `-wal`・`-shm` が別々に同期されて壊れる → **同期フォルダに置かない** |
| 論文の識別 | `papers.id`（端末ごとの AUTOINCREMENT）、`papers.sha256`（UNIQUE） | id は端末で違う → 同期の層では **sha256 で識別** |
| PDF | `files/<paper_id>/original.pdf`・`translated.pdf` | フォルダ名が端末ごとの id → 同期先では `papers/<sha256>/` に置く |
| 取り込み元のパス | `papers.source_path`（絶対パス。表示と記録のみ） | 端末に固有 → 同期しない |
| コレクション | `collections(id, name)`・`collection_papers(collection_id, paper_id)` | 端末をまたいで対応させるキーがなく、name は UNIQUE ではない → **`sync.sqlite3` で uid（UUID）と対応づける**（`library.sqlite3` は変えない） |
| 書誌情報 | `papers` の列。`edited`（手で直した項目）、`updated_at` は 1 つだけ | 項目ごとの更新時刻がない → 項目ごとの時計を追加 |
| 照会の状態 | `meta_status`（pending / done / failed / local） | 端末の状態 → 同期しない（結果の書誌情報だけを同期） |
| 訳文 | `translations`（1 論文 1 件）、`translated.pdf` は端末のフォント設定で組んだもの | 2 台で同時に翻訳すると衝突 → 端末ごとのファイルにし、規則で 1 つを選ぶ（§5.4） |
| 削除 | `Library.remove()` はレコードとファイルを消すだけ | 削除の記録（tombstone）がないと、別の端末から復活する → tombstone を追加 |
| 翻訳キャッシュ | `cache_dir()/translations.sqlite3`。キーは `sha256(namespace + "\0" + 原文)`、namespace はエンジン・言語・モデル・文体・プロンプトの版 | 端末固有の情報はなく統合も可能だが、OS に消されうる場所にあり、大きくなりうる → 同期しない（§4） |
| schema | `PRAGMA user_version` と `MIGRATIONS`。新しすぎる DB は開くのを拒む | 同期のために DB を上げると、古いアプリでライブラリが開けない → 同期データには DB と別の **format 版数**を持たせ、未知の項目は無視する |
| 設定 | `settings.json`（schema 3）。最後に開いたフォルダ・ウィンドウの位置などの端末固有の値を含む | 同期しない。同期の設定を足すときは schema 4 にする |
| 画面 | PDF が必ず手元にある前提（`open_paper`・翻訳ジョブ・見積もり・「Finder で表示」） | 「未ダウンロード」の状態を足すなら、すべての入口で取得を挟む（§7.3） |

## 4. 同期の対象と容量

| 対象 | 同期 | 理由・注意 |
|---|---|---|
| 書誌情報・お気に入り・コレクション | する | 機能の中心。容量は小さい |
| 原文 PDF | する | 読むのに必要。内容のハッシュを名前にするので変わらず、競合しない |
| 訳文 PDF とその情報 | する | 翻訳した端末のフォントで組んだまま、別の端末でも同じ見た目で読める。端末ごとのファイル |
| 翻訳キャッシュ | しない | ただのキャッシュで、訳文 PDF を同期すれば読むのに不要。文体などを変えて再翻訳するときの無料枠の節約は、段階 3 で論文ごとの形として検討する |
| API キー | しない | 秘密の情報。端末ごとに入力する |
| 設定・端末ごとの状態 | しない | 端末に固有 |

**容量の目安**（f3）: 原文と訳文で 1 本 2〜10 MB、500 本で 1〜5 GB。Google Drive の無料枠（15 GB）に収まるが、
設定画面に使用量を表示する。手元のライブラリと同期フォルダの両方に PDF を置くと、手元のディスクは 2 倍使う（§5.5）。

## 5. 同期方式とデータモデル（f3）

### 5.1 比べた案

| 案 | 内容 | 採否 |
|---|---|---|
| A | 論文ごとに 1 つの `paper.json` を全端末で共有 | 不採用。2 台が同じファイルを書くと、同期アプリが競合コピーを作るか黙って上書きする |
| **B** | **各端末は自分の名前のファイルにだけ書き、読む側が全端末の分をマージする** | **採用**。同じファイルを複数の端末が書かないので、競合コピーがほぼ起きない |
| C | 端末ごとの更新ログ（jsonl）を追記 | 不採用。ログの圧縮・再生順・欠けの扱いが重い。B は「状態」なので欠けを気にしなくてよい |
| D | SQLite を同期フォルダに直接置く | 不採用。WAL が壊れる |

### 5.2 フォルダの構成

```
Spectra Sync/
  format.json                       {"format": 1}  最初に作るときに一度だけ書く印。以後は書き換えない
  devices/<端末ID>.json              {"kind": "device", "device": 端末ID, "name": 端末名, "app": アプリの版, "format": 書き込む形式の版}（変わったときだけ書く）
  papers/<sha256>/
    original.pdf                    内容は変わらない。まだ無いときだけ書く
    state.<端末ID>.json              書誌情報・お気に入り・所属コレクション・追加と削除のイベント
    translated.<端末ID>.pdf
    translation.<端末ID>.json
  collections/<uuid>/state.<端末ID>.json   名前・削除の印
```

- **共有ファイルは書き換えない**: `format.json` は 2 台が同時に作っても内容が同じなので無害。形式の版を上げるときも `format.json` は書き換えず、
  各端末が `devices/<端末ID>.json` に `"format": n` を書き、読む側はその最大値を見る。自分の対応する版より新しければ、同期だけを読み取り専用にして更新を促す
  （手元のライブラリは開ける）。

### 5.3 識別子と、ローカルの同期情報（`sync.sqlite3`）

- 論文は sha256 で識別する。中身が違うファイル（出版版とプレプリントなど）は、今と同じく別の論文。
- コレクションには UUID を付ける。
- 端末 ID は uuid4 で、`config_dir()/device.json` に置く。設定ごとコピーされて重複した場合は作り直す。
- 同期の情報は、`library.sqlite3` とは別の `library/sync.sqlite3` に置く（e7 の提案に f3 が同意）。
  `library.sqlite3` の版を上げないので、v0.2.0 に戻してもライブラリが開ける。
  - 項目ごとの時計: (論文 sha, 項目, HLC, 手で編集したか)
  - tombstone: (sha256, HLC)
  - コレクション: ローカルの id と uid の対応、名前の HLC、削除の印
  - コレクションの所属: (コレクション uid, 論文 sha, 追加か削除か, HLC)
  - 訳文: (論文 sha, 端末, HLC, PDF の sha)
  - 書き出し・取り込みの状態: 最後に書き出したときの論文の行の内容のハッシュ、同期フォルダの各 JSON の (サイズ, mtime)
- **時刻の記録は `Library` の中に閉じ込め、UI からは見えない形にする**（e7）。
  f3 の方式: 起動時と走査時に、`library.sqlite3` の行と「最後に書き出したときの内容のハッシュ」を比べ、
  違っていた項目だけに新しい HLC を付ける。`Library` の更新処理にフックを入れずに済み、
  2 つの DB にまたがるトランザクションが原子的でない（SQLite の WAL の仕様）ことによるずれも、この比較で吸収できる。

### 5.4 マージの規則

- **時刻**: HLC（壁時計の時刻, カウンター, 端末ID）。相手の HLC が先に進んでいれば自分の時計をその後に進めるので、
  時計の遅れた端末でも、相手の変更を見たあとの操作は必ず後になる。ファイルの mtime は使わない。
- **書誌情報**: 項目ごとに (手で編集したか, HLC, 端末ID) が最大の値を採用する。手で直した値は、
  別の端末であとから自動取得した値にも負けない（今の `edited` の約束を端末をまたいでも保つ）。
- **お気に入り**: LWW。**最後に開いた日時**: 最大値（どの端末で開いても「最近開いた」がそろう）。
- **コレクションの所属**: (コレクション uid, 論文 sha) の組ごとに「追加」「削除」の LWW。コレクションごとに一覧を丸ごと持つと、
  2 台で別々の論文を同時に追加したときに片方が消えるため（e7）。名前の変更とコレクションの削除は、コレクション単位の LWW と tombstone。
- **論文の存在**: 追加と削除のイベントのうち、HLC が最新のもので決める。編集だけでは復活しない（§12 Q6）。
- **削除の種類**（f3・e7・5d が一致）:
  - 「このパソコンのコピーを削除（クラウドには残す）」: 手元の PDF と訳文だけを消し、論文は ☁ として一覧に残る。tombstone は書かない。開くともう一度取得する。
  - 「ライブラリから削除」: tombstone を書き、すべての端末から消える。
- **訳文**: 端末ごとのファイルなので衝突しない。表示するのは (全ページを欠けなく訳せている, 訳したページの範囲, HLC) が最大のもの。
  負けた端末は自分の訳文ファイルを消す（各端末は自分のファイルだけを消す）。古い訳文を残すかは §12 Q7。
- マージは状態から行い、同じ入力からは必ず同じ結果になる（何度取り込んでも結果が変わらない）。

### 5.5 書き込み・読み込み・監視

- JSON は同じフォルダに `.tmp` で書いてから名前を変える。読めない JSON は「まだ届いていない」とみなして次の走査で読み直す。
- PDF は sha256 で検証してから取り込む。一致しないもの・無いものは「未ダウンロード」として扱う。
- **約束: 同期フォルダのファイルは、UI のスレッドから決して直接読まない。** 読み書きはすべてワーカー（同期のキュー）で行う。
  PDF は `library_dir()/files/<id>/` に `.tmp` でコピーし、sha256 を検証してから名前を変える。ファイルごとにタイムアウトとキャンセルを設け、
  失敗したら次の走査で再試行する。読書画面とライブラリは、常に手元のコピーだけを開く。
  理由: Google Drive の「ストリーミング」や、Dropbox・OneDrive のオンライン専用ファイルは、手元にあるように見えても、
  読んだ瞬間に OS がダウンロードを始めて読み込みが止まるため。書き出し（手元 → 同期フォルダ）も、大きな PDF で UI が固まらないようワーカーで行う。
- 論文ごとのファイルの状態（UI はこれを映す）:

  | 状態 | 判定 |
  |---|---|
  | 取り込み済み | 手元にコピーがある（コピーするときに sha を検証してから名前を変えるので、手元にあれば一致している。開くたびには計算しない） |
  | 取得中 | コピーの途中 |
  | 未取得 | 同期フォルダに実体がある（または `.icloud` のプレースホルダーだけがある）が、手元にない |
  | 到着待ち | 書誌情報は届いたが、PDF がまだ同期フォルダに届いていない（5d） |
  | 接続できない | 同期フォルダ自体が見つからないか、読めない |

- 「オフライン」かどうかは OS のネットワーク状態では決めない。Spectra に分かるのは、同期フォルダが読めるかと、PDF のハッシュが合うかだけ。
- 競合コピー（`state.X (1).json` など）は、`papers/<sha>/` の `*.json` をファイル名に関係なくすべて読み、中に書かれた端末 ID の分としてマージする。
  PDF は内容のハッシュで照合し、正しい名前以外のファイルは無視する。持ち主の端末があとで整理する。
- 監視: `QFileSystemWatcher`、60 秒ごとの走査、アプリが前面に来たときの確認。
  ディレクトリの一覧と JSON の (サイズ, mtime) を変更の手がかりにし、**変わった JSON だけを解析する**（起動を重くしない）。
  mtime は手がかりに使うだけで、競合の判断には使わない。PDF は、手元にないか sha が合わないときだけ読みに行く。
- 同期フォルダの場所: ユーザーが選んだフォルダの中に「Spectra Sync」を作る。サービスごとの決まった場所を自動で使うことはしない
  （サービスや言語でパスが変わり、壊れやすい）。候補として示すだけ（§7.1）。

### 5.5.1 各サービスでの動作（f3）

| サービス | 手元にないファイル | 競合コピーの名前 | Linux |
|---|---|---|---|
| Google Drive for desktop | 「ストリーミング」では開いたときにダウンロード（「ミラーリング」なら常に手元） | `name (1).json` | 公式アプリなし（rclone・Insync を案内） |
| Dropbox | オンライン専用は開いたときにダウンロード | `name (端末名's conflicted copy 日付).json` | 公式アプリあり |
| OneDrive | Files On-Demand は開いたときにダウンロード | `name-端末名.json` | 公式アプリなし |
| iCloud Drive | 「ストレージを最適化」で `.name.icloud` に置き換わり、元の名前のファイルが無くなる | — | — |
| Syncthing・NAS | 常に手元 | `.sync-conflict-…` | あり |

- iCloud の `.X.icloud` は「未取得」として扱い、macOS では `startDownloadingUbiquitousItem`（または `brctl download`）で取り寄せる（段階 2 でもよい）。
- 大文字と小文字を区別しないファイルシステムがあるので、ファイル名は小文字の 16 進と固定の名前だけにする。
- Windows のパスの長さ（約 260 文字）を考え、階層は浅くする。
- 同期の処理は、翻訳キュー・照会キューと同じく、バックグラウンドの直列のキューで行う（`Library` は lock 付きでワーカーから使える）。
- 構成: `SyncStorage`（list / read / write_atomic / delete）を抽象として置き、まず `FolderStorage` を実装する。
  マージ（`library/sync.py`）は方式に依存しない純粋な関数にし、将来 `DriveStorage` を差し込めるようにする。

### 5.5.2 ローカルの変更に HLC を付ける規則（f3・e7 が合意）

- **合図**: `Library.add_listener(fn)` を、コミットしてロックを離した後に呼ぶ（Qt に依存しない）。同期の層は約 2 秒の遅延をおいてローカルを走査する。起動直後にも走査する。UI に呼び出しを足す必要はない。
- **時刻**: HLC の壁時計の部分には、行の `updated_at`（編集した時刻）を使う。新しい HLC は `max(updated_at のミリ秒, 時計の最新 + 1)`。
  オフラインの間の操作や、別のプロセス（CLI）での操作にも、編集した頃の時刻が付く。
  コレクションと所属だけは走査した時刻を使う（合図で直後に走査するので、ずれは数秒）。`last_opened_at` は最大値を採るので HLC は要らない。
- `set_meta_status` は `updated_at` を進めない（照会の状態は同期しないので、書誌情報の HLC をずらさない）。
- **順序**: 他の端末の変更を反映する直前に、必ずローカルを走査する（まだ時刻の付いていないローカルの変更が上書きされないように）。
- **エコーの防止**: 反映は `sync.sqlite3` の `pending_apply` に記録 → library を更新 → 行のハッシュと相手の HLC を記録 → `pending_apply` を消す、の順。
  起動時に `pending_apply` が残っていれば、library の行と照らして完了させる。
- **手で直したか**: 走査で変更を見つけた項目が library の `edited` に入っていれば「手で直した」、そうでなければ「自動」。

### 5.5.3 core と UI の境界（f3・e7 が合意）

- `Library.add_listener(fn: Callable[[LibraryEvent], None]) -> 解除の関数` — ローカルの変更を同期の層に知らせる。
- `SyncEngine.add_remote_listener(fn: Callable[[list[RemoteChange]], None]) -> 解除の関数` — 他の端末の変更を反映したとき、1 回の反映でまとめて 1 回だけ呼ぶ（同期のワーカーのスレッドから）。
  - `RemoteChange(kind: "added" | "metadata" | "translation" | "removed" | "collections" | "file", sha256: str, paper_id: int | None, fields: frozenset[str])`
    （`removed` のときの `paper_id` は削除する前の id、`fields` は `metadata` のとき）
- リスナーの約束（両方に共通）: ① コミットしてロックを離した後に呼ぶ ② 例外は `log.exception` に書いて握りつぶす ③ リスナーは合図だけを受け取り、重い処理はしない ④ 呼ばれるスレッドは決まっていない（UI は Qt のシグナルに乗せ換える）。
- 新しい例外 `PaperNotFound(LibraryError)`: 論文が見つからないときに送出する。翻訳のワーカーの中では `CancelledError` と同じに扱う（他の端末から削除された場合にエラーのダイアログを出さない）。
- `SyncEngine.fetch(paper_id, kind: "original" | "translation", progress: Callable[[int, int], None] | None = None, cancel: threading.Event | None = None) -> Path`
  — 1 件を取得する、処理が終わるまで戻らない関数（ワーカーから呼ぶ）。手元にあれば、同期フォルダに触らずすぐに返す。
  手順は `.tmp` にコピー（`progress` は (読んだバイト数, 全体)。全体が分からなければ 0）→ sha256 で検証 → rename → `"file"` の `RemoteChange` を出す。
  - 例外: `SyncError(SpectraError)` の子として、`SyncUnavailable`（同期フォルダを読めない）、`RemoteMissing`（同期先にまだファイルがない）、
    `HashMismatch`（同期の途中か、壊れている）。それぞれ日本語の title と hint を持ち、UI はそのまま表示する（文言は §7 に合わせる）。
    論文が無いときは `PaperNotFound`、キャンセルは翻訳と同じ `CancelledError` で、`.tmp` は消す。
  - 取得の待ち行列と進捗の表示は UI 側に持つ（翻訳キューと同じ作り）。
- `Paper.has_original` / `Paper.has_translation_file`（bool）: 読み込むときに、手元のファイルがあるかだけで 1 回決める（同期フォルダには触らない）。一覧の ☁ の表示に使う。
  - `has_original`: 同期が無効なら常に True。
  - `has_translation_file`: 「訳文があり、かつ訳文のファイルが手元にある」。未翻訳の論文は、同期の有無に関係なく False。
  - UI は、`has_original` が False なら原文が ☁、`translation is not None and not has_translation_file` なら訳文が ☁ と判断する。

### 5.6 初回の同期と既存ライブラリの統合

- 同期をオンにしたとき: 既存の論文すべてに HLC として `updated_at` を割り当て、state を書き出し、PDF をコピーする。
  PDF は sha で存在を確認してから書くので、途中で止まっても再開できる。進み具合はバックグラウンドで表示する。
- 2 台目に既存のライブラリがある場合も同じ手順で、同じ sha の論文は項目ごとのマージで 1 件になる。
  DOI だけが同じものは、v0.2.0 と同じく別の論文として残す。確認は出さず、結果をバナーで知らせる（§7.4）。
- 同じ名前のコレクションは、uid がまだ付いていない初回の接続のときだけ 1 つにまとめる（§12 Q10）。
  その後に 2 台でたまたま同じ名前のコレクションを作った場合は、別の uid として残す。
- 統合の前に、手元のライブラリを自動でバックアップし、一度だけ「同期前の状態に戻す」をできるようにする（このリリースに入れる）。
  - `SyncEngine.backup_before_first_sync()`: 初回だけ `library.sqlite3` と `state.sqlite3` を `library-backups/<日時>/` に SQLite のバックアップ API で写す（PDF は写さない）。`sync_now` が初回の統合の前に自動で呼ぶ。
  - `SyncEngine.backup_path`: 作ったバックアップの場所（設定の「同期」タブに「同期前の状態に戻す…」を出すかの判断）。
  - `restore_backup(path)`: Library と SyncEngine を閉じてから呼ぶ。DB を書き戻し、`sync.sqlite3` を消す。UI は同期をオフにして保存し、Library を開き直す。同期をオンにしたまま戻すことはしない。
- 不整合に備えた「同期フォルダから作り直す」操作は段階 3 に回す（マージは何度行っても結果が変わらないので、通常は不要）。

## 6. 連携方式の比較

| 観点 | **同期フォルダ方式（採用）** | Google Drive API 方式（将来の候補） |
|---|---|---|
| 対応サービス | Google Drive・Dropbox・OneDrive・iCloud・NAS・Syncthing など、同期フォルダがあればどれでも | Google Drive のみ |
| 認証 | 不要（同期アプリが行う） | OAuth。トークンを OS の資格情報ストアに保存し、ログアウトの操作が必要 |
| 運用負担 | なし。新しい依存もない | OSS に OAuth クライアントを入れることになり、同意画面の審査が要る（`drive.file` スコープなら軽いはずだが要確認） |
| Spectra の通信 | 増えない（README・SECURITY.md の約束を保てる） | Google Drive が増える |
| 弱点 | 同期アプリの動きに左右される（競合コピー・ストリーミング・遅延）。§5.5 で吸収する。デスクトップアプリが必要で、**Linux には Google 公式のアプリがない** | 実装とテストの範囲が大きい（再開できるアップロード、API の上限、トークン失効） |
| テスト | 一時フォルダだけで完結 | API の疑似環境が必要 |

## 7. UI/UX（5d、e7 のレビューを反映）

方針: 同期は裏で静かに動かし、選ばせることはできるだけ減らす。ライブラリの使い勝手は同期の有無で変えない。
専門用語（同期フォルダ、OAuth、競合、トークン）は画面に出さない。主ボタンは各画面に 1 つ、単色。

### 7.1 設定の「同期」タブ

設定ダイアログに「同期」タブを追加する（並びは 翻訳エンジン / フォント / 同期 / 詳細）。

接続前（同期フォルダが見つかった場合）:

```
┌ 別のパソコンと同期 ──────────────────────────────┐
│ ライブラリ・原文・訳文を、ほかのパソコンの Spectra でも開けるようにします。 │
│                                                                  │
│ Google Drive（me@example.com）            [ このフォルダを使う ] │
│ Dropbox                                   [ このフォルダを使う ] │
│ ほかのフォルダを選択…                                            │
└──────────────────────────────────────────┘
PDF と書誌情報を保存先に置きます。API キーと設定は同期しません。
```

- 同期フォルダの候補を探して並べる（macOS の `~/Library/CloudStorage/GoogleDrive-*`・Dropbox・iCloud Drive、Windows のそれぞれの既定の場所）。
  見つからなければ「フォルダを選択…」だけにする。正しいフォルダを見つけられないことが一番のつまずきになるため（5d）。
- 選んだフォルダが既知の同期先の外なら、止めずに caption で「このフォルダは、ほかのパソコンと同期されていない可能性があります」。
- 選んだフォルダに Spectra のデータがあれば「このフォルダのライブラリを使います（論文 N 件）」、なければ「Spectra Sync」を作る。

接続後:

```
┌ 同期 ──────────────────────────────────────────┐
│ 保存先          Google Drive › Spectra Sync                [変更…] │
│ 同期する                                              (●)        │
│ 最後に保存      今日 14:32                       [今すぐ同期]     │
│ 使用量          1.2 GB                                             │
└──────────────────────────────────────────┘
オフラインでも読みたい場合は、同期アプリでこのフォルダを「オフラインで使用可能」にしてください。
  接続を解除…
```

- 保存先はパスではなく短い名前で示し、パスはツールチップに出す。
- 手元への取得のタイミング（開いたときだけ / すべて）は §12 Q3 で決める。クラウドからの取得は同期アプリの設定なので、Spectra では扱わない。
- 解除の確認文: 「同期をやめます。このパソコンのライブラリはそのまま残り、同期先のデータも削除しません。」

### 7.2 有効にするときの説明（5d・e7 の文案を統合）

「同期を始める前に」のシートを、最初の 1 回だけ出す。

> 同期をオンにすると、ライブラリの論文の PDF（原文・訳文）・書誌情報・コレクションを、選んだフォルダに保存します。
> そのフォルダを Google Drive などで同期している場合は、そのサービスにアップロードされ、各サービスの規約に従って扱われます。
> Spectra の開発者がこれらのデータを受け取ることはありません。
> 未公開の原稿や、共有が禁止されている論文が含まれる場合は、所属先の規則を確認してください。API キーと設定は同期しません。
>
> [キャンセル] [同期を始める]

### 7.3 状態の表示と、手元にない論文

サイドバーの一番下（「＋ 新しいコレクション」の上）に 1 行だけ出す。同期がオフなら出さない。読書画面には出さない。

| 表示 | 状態 |
|---|---|
| ✓ 保存済み · 2 分前 | 通常（secondary の色）。Spectra に分かるのは「同期フォルダに書いた」ところまでなので、「同期済み」とは言わない（5d） |
| ⟳ 同期中… 3 / 12、↓ 取得中… 2 件 | 進行中 |
| ⏸ 同期を一時停止中 | オフにしている |
| ⚠ 同期できませんでした [詳細] | 失敗（warning の色） |

- 「オフライン」の状態は出さない（Spectra には判定できない）。ファイルを取得できなかったときに、その場で知らせる。
- クリックでポップオーバー: 最後に保存した時刻、未保存の件数、「ほかのパソコンからの最後の変更: 3 日前（MacBook Air）」、
  「クラウドへの反映は同期アプリ（Google Drive など）が行います」の一文、[今すぐ同期]、[設定を開く]。
- 「しばらく更新されていない」は警告にしない。ほかのパソコンを使っていないだけでも同じに見えるので、ポップオーバーに事実だけを出す。
- 記号と文字の両方で示し、色だけに頼らない。読み上げは「同期の状態: 保存済み、2 分前」。

手元にない論文（e7 のレビューを反映）:

- 一覧: タイトルの**左**に記号を `DecorationRole` で置き、読み上げ用の文字を付ける。手元のライブラリにコピーがあるかは Spectra が確実に知っているので、印は正確に出せる。
  - ☁ 未取得（「このパソコンにまだありません」）、↓ 取得中、⏳ 到着待ち（「ほかのパソコンからファイルが届くのを待っています」。「読む」は無効）
- 取得は、翻訳キューと同じく**バックグラウンドの取得のキュー**にまとめる。論文ごとの状態（§5.5）を 1 か所に持ち、
  行の記号・フッター・詳細パネルの「読む」ボタンがそれを映す。開く入口（詳細パネル、ダブルクリック・Enter、右クリック、バナー、起動時の引数）はすべて同じ動きにする。
- 取得中は、全体の大きさが分かれば割合（「ファイルを取得中… 45%」）を、分からなければ回転する表示を出し、[キャンセル] を付ける
  （`fetch` の `progress` は全体が分からないとき 0 を渡す。ストリーミングでは分からないことがある）。
- **30 秒間まったく進まなかったら**（全体の時間ではない。大きな PDF を遅い回線で取得していると、正常でも 30 秒を超えるため）、
  「ファイルを取得できませんでした。同期アプリ（Google Drive など）が動いているか確認してください」[再試行]。
- `open_paper` は「手元にあれば今までどおり開く、なければ取得してから開く」の 2 段階に分ける。
- 翻訳キューに入れた場合は、ワーカーの最初に「ダウンロードしています」の段階を足す。見積もりはダウンロードが終わるまで「—」。
- 同期先に接続できないときは、**手元にコピーがない論文に限り**「読む」「翻訳する」を無効にし、ツールチップに理由を書く。
  手元にある論文は、今までどおり読めて翻訳もできる（同期の有無で使い勝手を変えない）。BibTeX と情報の編集は使える。
- 「Finder で表示」は、未ダウンロードの論文では（オンラインでも）出さない。
- 詳細パネルの「AI翻訳の詳細」に「このパソコン: 保存済み / 未取得 / 取得中」の行を足す。
- 右クリックに「このパソコンに保存」「このパソコンのコピーを削除（クラウドには残す）」を足す。後者は容量を空けるだけで、論文は ☁ になって残る。

### 7.3.1 段階 1 の「読むだけ」のパソコン（e7 の指摘で追加）

> **出荷しない**（§0 の Q5 の帰結）。段階 1 と 2 を同じリリースに入れるので、利用者に見える役割は作らない。以下は検討の記録。

段階 1 では、書き出すパソコン（メイン）は 1 台だけ。

- **役割の決め方**（f3）: 各端末は自分の `devices/<端末ID>.json` に `"primary_claim": <HLC>` を書く。
  メインは「`primary_claim` の (HLC, 端末 ID) が最大の端末」で、各端末がそれぞれ計算する。共有ファイルは書き換えない（端末ごとに単一の書き手の原則を守る）。
  - 同期フォルダを最初に作ったパソコンは、作成時に宣言を書く。あとから接続したパソコンは宣言を書かないので、読むだけになる。
  - 設定の「同期」タブに「このパソコン: 読むだけ（メイン: MacBook Pro）」と表示し、[このパソコンをメインにする…] で、自分のファイルに新しい宣言を書く。
    古いメインは、新しい宣言を読んだ時点で自動で読むだけになる。
  - 切り替えの確認（5d・e7）: メインが最近使われていれば「MacBook Pro で 3 分前に使われています。MacBook Pro を閉じてから切り替えてください。」、
    そうでなければ「MacBook Pro は読むだけになります。両方で同時に使っていないことを確認してください」。
    このパソコンだけにある論文があれば「このパソコンだけにある N 件の論文も同期されます」を添える。[キャンセル] [切り替える]
  - 古いメインがオフラインの間だけは、2 台が「自分がメイン」と思って書く可能性がある。データの形は最初から複数の端末が書いてもマージできる B なので、データは壊れない。
    **段階 1 の「読むだけ」は、データを守る仕組みではなく、競合を見せないための UI の簡略化**と位置づける。
  - 切り替えは段階 1 の間の暫定の操作で、段階 2 では役割がなくなる。
- **読むだけのパソコンで無効にする操作**（同期した論文について）: 追加・削除・書誌情報の編集・お気に入り・コレクションの変更・翻訳。
  翻訳を許すと、同期されない訳文が手元にだけ残るため。無効にした操作のツールチップは「読むだけのパソコンでは変更できません（メイン: MacBook Pro）」。
  「このパソコンのコピーを削除（クラウドには残す）」「このパソコンに保存」「BibTeX をコピー」は使える（手元だけの操作か、読むだけの操作なので）。
- 無効の理由が分かるように（5d）:
  - 接続した直後に一度だけ、バナー（info）で「このパソコンでは読むだけです。論文の追加・編集・翻訳は、メインの MacBook Pro で行ってください。」[このパソコンをメインにする…]
  - 詳細パネルで「翻訳する」が使えない論文では、ボタンの下に caption で「翻訳はメインのパソコン（MacBook Pro）で行えます」（macOS ではツールチップが気づかれにくい）。
  - 右クリックメニューの無効の項目は、隠さず灰色で残す。
- サイドバーの状態の行は、既存の "eye" アイコン（線のアイコン。絵文字は使わない）と「読むだけ · 2 分前に反映」にする。
  ほかの状態の記号（✓ ⟳ ⚠）も、実装では icons.py のアイコンにする。
- **論文の追加**（Q12 が ① の場合。e7・5d）: 読むだけのパソコンでも PDF を追加でき、その論文は手元だけ（同期しない）になる。
  「論文を追加」のボタン・⌘O・ドロップは有効のまま（無効の主ボタンを目立つ場所に残さない）。Q12 が ② や ③ の場合は、同期したライブラリの表示中は隠す。
  - 追加した PDF の sha256 が同期した論文と同じなら、新しい論文は作らず、その論文の「このパソコンに保存」と同じ扱いにする。
  - そのパソコンをあとからメインにしたときや、段階 2 に上がったときは、手元だけの論文も同期の対象になる。
- **読むだけのパソコンに、もともと手元の論文がある場合**は §12 Q12 で決める。

### 7.4 別のパソコンで最初に開いたとき

- 空のライブラリ画面に、主ボタン「論文を追加」とは別のリンク「別のパソコンのライブラリを同期…」を置く。
- 接続すると書誌情報の一覧がすぐに現れ、一度だけバナー（info）で「ライブラリを同期しました（論文 42 件）。論文を開くと、ファイルをダウンロードします。」。
- 手元にも論文があれば自動でまとめ、「このパソコンの 5 件と合わせて 47 件になりました」と知らせる。

### 7.5 削除とゴミ箱（e7 案。ゴミ箱は段階 2 = このリリース）

- **ゴミ箱は、同期が無効のときも使う**（削除はいつもゴミ箱に入る）。同期の有無で削除の動きを変えずに済み、誤って消した論文も戻せる。
  v0.2.0 からの動きの変更なので、CHANGELOG に書く（推奨で進行。§0 に追記）。
- 削除の伝達（tombstone）は段階 1 から入れる。tombstone がないと、同期が有効な間は論文を本当に消す手段がない。
- 「このパソコンのコピーを削除（クラウドには残す）」は削除とは呼ばず、右クリックの別の項目にする。1 つのダイアログに選択肢を並べない。

画面:

- サイドバー: ライブラリの項目の一番下に「ゴミ箱」（件数があれば「ゴミ箱 3」）。
- ゴミ箱の一覧: 同じ表で、「追加日」の列の代わりに「削除した日」。検索も効く。ゴミ箱の論文は、ほかの絞り込み（すべて・お気に入り・コレクション）には出さない。
- 詳細パネル: タイトル・著者と「あと N 日で完全に削除されます」、主ボタン「ゴミ箱から戻す」、「完全に削除…」（destructive）。「読む」と「翻訳」は出さない（戻してから使う）。
- 右クリック: ゴミ箱の中では「ゴミ箱から戻す」「完全に削除…」だけ。ゴミ箱を選んでいるときは、一覧の上に「ゴミ箱を空にする…」。
- アイコン: 5d の "trash"・"restore"。

確認の文言:

| 操作 | 文言 |
|---|---|
| 削除（同期あり） | 「ライブラリから削除しますか？ すべてのパソコンから削除されます。30 日以内ならゴミ箱から戻せます。元のファイルは残ります。」[キャンセル] [削除] |
| 削除（同期なし） | 「ライブラリから削除しますか？ 30 日以内ならゴミ箱から戻せます。元のファイルは残ります。」 |
| 完全に削除 | 「完全に削除しますか？ この操作は取り消せません。」（同期ありなら「すべてのパソコンから」を加える） |
| ゴミ箱を空にする | 「ゴミ箱の N 件を完全に削除しますか？ この操作は取り消せません。」 |

core の API（f3）: `trash`・`restore`・`purge`・`empty_trash`・`purge_expired`（30 日）・`trashed_papers`・`Paper.trashed_at`。

- ゴミ箱の状態は、`library.sqlite3` の隣の **`library/state.sqlite3`** に `trash(paper_id, trashed_at)` として持ち、`Library` の接続で ATTACH する（f3 案 a）。
  `library.sqlite3` の `user_version` は 1 のまま。ゴミ箱は同期が無効でも使うので、`sync.sqlite3` とは分ける。
  - 入れる・戻すは片方の DB に 1 行書くだけなので原子的。完全に削除は 2 つの DB にまたがるので、起動時に、論文がなくなった `trash` の行を掃除する。
  - v0.2.0 に戻すと、ライブラリは開け、ゴミ箱の論文が普通の論文として見える（データは失われない）。
- `papers()` はゴミ箱の論文を含めない。今の `remove()` は `purge` の別名として残す（CLI と今までの呼び出し元のため。画面の「削除」は `trash` を呼ぶ）。
- ゴミ箱にある PDF をもう一度取り込んだら、ゴミ箱から戻して `(既存の論文, True)` を返す。
- 同期の層では、ゴミ箱に入れたら tombstone を書き、戻したら tombstone より新しい追加のイベントを書く。完全に削除しても tombstone は残す。

### 7.5.1 他の端末の変更を反映したとき（e7）

`RemoteChange` の通知（§5.5.3）を受けて、UI は次のように動く。

| 場面 | 動作 |
|---|---|
| どの変更でも | 一覧と詳細パネルを更新する |
| 読書画面で開いている論文の訳文が、別の端末で更新された | いきなり差し替えず、バナーで「別のパソコンで新しい訳文が作られました」[開き直す] |
| 開いている論文が、別の端末で削除された | ライブラリに戻し、「この論文は別のパソコンで削除されました」と知らせる |
| 翻訳中・待機中の論文が削除された | キューから外す（エラーのダイアログは出さない） |

### 7.6 失敗の表示

どれもローカルでの利用を止めず、自動で再試行する。バナーは操作が必要なときだけ出す。

| 失敗 | 表示 |
|---|---|
| 同期先のフォルダが見つからない（外付けドライブが外れたなど） | バナー（warning）「同期先のフォルダが見つかりません。外付けドライブや同期アプリを確認してください」[フォルダを選び直す] |
| 自動で取り込めない競合コピー | バナー「同期アプリが作った重複したデータを見つけました」[まとめる]（自動で取り込めるものは知らせない） |
| このパソコンの容量不足 | 「このパソコンの空き容量が足りないため、3 件の論文を保存できませんでした」。クラウド側の容量不足は Spectra には分からず、同期アプリが知らせるので扱わない |
| 新しい形式（format）のデータ | 「別のパソコンで新しい Spectra が使われています。このパソコンの Spectra を更新してください」（読むだけにして、データは壊さない） |
| 一時的なエラー | バナーは出さず、状態の行を「⚠ 同期できませんでした — 自動で再試行します」に |

詳しい情報（失敗した論文と理由）はポップオーバーの [詳細] に置き、エラーコードは出さない（ログには残す）。

## 8. プライバシーとセキュリティ（97）

### 8.1 外部への通信の記述

同期フォルダ方式では Spectra 自身の通信先は増えない。ただし論文と訳文が同期サービスに置かれるので、記述を足す。

- **SECURITY.md「外部への通信」**: 「同期を有効にした場合（初期状態は無効）に限り、ライブラリの PDF（原文・訳文）・書誌情報・コレクションを、
  利用者が選んだフォルダへ保存します。そのフォルダを同期するサービスへのアップロードは、そのサービスのアプリが行います。
  Gemini の API キー、その他の設定、翻訳キャッシュは同期しません。」
- **README（FAQ「論文の内容はどこかに送信されますか？」）**: 「ライブラリの同期を有効にした場合は、PDF・訳文・書誌情報を、選んだフォルダに保存します。
  Spectra 自身は通信せず、そのフォルダを同期するサービス（Google Drive など）がアップロードします。同期は初期状態では無効です。」
- **DESIGN.md §6**: 同じ内容を追加する。
- 将来 Drive API 方式を足す場合は、送信先に Google Drive を加え、トークンの保存場所（OS の資格情報ストア）と権限の範囲（`drive.file` または `appDataFolder`）を明記する。

### 8.2 オプトイン

既定でオフ。書誌情報の照会（識別子だけを送る）と違い、論文の本文そのものを第三者のサービスに置くため。説明は §7.2。

### 8.3 PDF をクラウドに置くことの注意

- 購読契約で入手した論文は、個人の複数端末での利用が認められていても、共有フォルダへの配置は認められていないことがある。
  同期フォルダをほかの人と共有しないよう、説明とヘルプで案内する。
- 未公開の原稿や査読中の論文などは、同期の対象から外せると安全（段階 3 の「同期する範囲の選択」）。
- 同期フォルダの中身の暗号化は、各サービスに任せる（§12 Q8）。

### 8.4 認証情報

- API キーは同期しない。別のパソコンでは、そのパソコンで API キーを設定する（同期した訳文を読むだけならキーは不要）。
- 同期フォルダ方式では、Spectra は認証情報を持たない。

### 8.5 同期データは外部入力として扱う

同期フォルダの中身は、ほかの端末やほかのアプリが書き換えうる。

- JSON はスキーマを検証し、壊れたもの・未知の format は取り込まない（例外で落ちない）。未知の項目は無視する。
- ファイル名は `papers/<64 桁の 16 進>/` と既知の名前だけを受け付け、`..`・絶対パス・シンボリックリンクを拒否する。
- PDF は sha256 を照合してから取り込む。
- JSON の文字列の長さや件数に上限を設ける（巨大なファイルでメモリを使い切らない）。
- 端末名など、ほかの端末から来た文字列は、画面に出すときにリッチテキストとして解釈しない。

## 9. 段階的な導入

| 段階 | 内容 | 競合 |
|---|---|---|
| 1. 読むだけ | 1 台を「書き出す端末」にし、ほかの端末は読み取り専用でライブラリ・原文・訳文を閲覧する。書き出す端末での削除（tombstone）もほかの端末に届ける。形式は最初から B（複数の端末が書く前提）にするので、次の段階で形式を移す必要はない | 起きない |
| 2. 双方向 | 全端末で、追加・削除・お気に入り・書誌情報の編集・コレクション・翻訳を書ける。**ゴミ箱と取り消し（30 日）**。iCloud のプレースホルダーの取り寄せ | 自動で解決（§5.4） |
| 3. 整理と拡張 | 不要なファイルの整理、翻訳キャッシュの共有（オプトイン）、同期する範囲の選択（訳文だけ・コレクションごと） | — |

**最初のリリースは段階 1 と 2**（§0 の Q5）。段階 1 は実装の途中の節目としてだけ使い、利用者には「読むだけ」の役割を見せない。

ゴミ箱（段階 2）: 「ライブラリから削除」は tombstone を書き、論文をゴミ箱に移す（手元の PDF と訳文、書誌情報は 30 日残す）。
ゴミ箱から戻すと、tombstone より新しい HLC の追加のイベントを書くので、ほかの端末でも戻る。30 日を過ぎたら手元のファイルを消す。
同期フォルダの `original.pdf` の整理（どの端末も使っていないものを消す）は段階 3。

翻訳キャッシュを共有する場合の形（f3、段階 3）: 論文ごと・端末ごとの `papers/<sha>/cache.<端末ID>.jsonl.gz` に `{"k": cache_key, "t": 訳文}` を並べ、
取り込むときは手元にない key だけを入れる（手元を優先）。キーは端末に依存しないので和集合でよい。1 本あたり gzip で 50〜70 KB、500 本で 25〜35 MB。

## 10. テスト方針（ネットワーク不要）

2 つの `Library` と、`FakeFolderStorage`（一時フォルダを包み、遅延・順序の入れ替え・部分的な書き込みを注入できるもの）で 2 台の端末を再現する。
結果が決まるテストとして書く。

- 時計のずれ（1 時間。HLC を注入する）、同じ項目を 2 台で編集、手での編集と自動取得の優先
- 反映の直前のローカル走査（未記録のローカルの変更が上書きされない）、`pending_apply` が残った状態からの起動（エコーしない）
- 他の端末からの削除: 開いている論文・翻訳中の論文（`PaperNotFound` でダイアログを出さない）
- JSON が先に届き PDF が後から届く、途中まで書かれた JSON、途中までの PDF・欠けた PDF、壊れた JSON、未知の format（読み取り専用になる）
- 各サービスの名前の競合コピー、`.icloud` のプレースホルダー
- 同じ入力を 2 回マージしても結果が変わらない、途中で止めて再開する
- `library.sqlite3` と `sync.sqlite3` の間でアプリが落ちた場合（内容のハッシュの比較で回復する）
- 削除と編集が同時、同時に翻訳、コレクションの名前変更と所属の変更
- 同じ PDF を 2 台で別々に追加したときの統合、既存ライブラリの統合とバックアップからの復元
- 同期フォルダの読み込みが遅い・止まる（ストリーミングの疑似）ときに UI が固まらないこと
- 外部入力: パストラバーサル、巨大な JSON、不正な sha
- プライバシー: 同期がオフのとき同期フォルダに何も書かないこと、API キー・設定・翻訳キャッシュが書き出されないこと
- 画面（オフスクリーン、e7 が実装と一緒に書く）:
  - ☁・↓・⏳ の記号と読み上げの文字
  - 取得のキュー（どの入口から開いても同じ動き）、割合の表示と、30 秒間進まないときのタイムアウト
  - `RemoteChange` を受けたときの 3 つの動作（訳文の更新のバナー、開いている論文の削除、キューから外す）
  - 同期の有無による削除の文言の違い
  - 手元にある論文が、同期先に接続できないときも開けて翻訳できること
  - 段階 1 の読むだけのパソコンで、変更の操作が無効になること
- 移行: 同期をオンにすると `sync.sqlite3` が作られ、`library.sqlite3` の `user_version` は 1 のまま変わらず、v0.2.0 でも開けること
